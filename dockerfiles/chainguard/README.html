Chainguard Builds ​

TL;DR ​

From the HPCC-Platform repository root:

bash
./dockerfiles/chainguard/build.sh

This builds HPCC Platform and creates APK, DEB, RPM, and SBOM files using glibc 2.34 and GCC 11. Build files and packages go in:

text
build/chainguard-hpcc-glibc2.34-gcc11-amd64/

No LN checkout is required.

Setup ​

Use Docker or Podman with a running engine. macOS also supports Apple's container CLI; Windows supports Docker, Podman, or WSL containers (wslc.exe) from Git Bash.

The scripts automatically select the first usable runtime, trying Docker before Podman. An installed Docker CLI without a running engine does not prevent falling back to Podman. Set CONTAINER_RUNTIME=podman to explicitly select Podman. Each script reports the selected container runtime on stderr before doing any build work. Docker Hub image references are fully qualified, so Podman does not require short-name aliases or an unqualified-search registry configuration.

For access to the default JFrog images and shared dependency cache, create .env in the HPCC-Platform repository root:

bash
JFROG_USERNAME=your.name@example.com
JFROG_PASSWORD='your-password-or-PAT'

Keep credentials out of version control. The file is optional if the required images are already available locally. Set ENV_FILE to use another file.

The build automatically pulls the builder image, reuses a local image if the pull fails, or builds one if needed. The first build can take longer while dependencies are downloaded and compiled.

APK builds require unprivileged user namespaces. The script checks this before building and reports any required host configuration.

Common Build Options ​

OptionPurpose
--glibc <version>Change the glibc baseline; GCC follows the baseline unless overridden.
--gcc <major>Override the GCC version.
--arch amd64 or --arch arm64Select the architecture; defaults to the host.
-f deb,rpmBuild only the listed formats instead of all three.
-b <directory>Change the build directory.
-o <directory>Write packages and SBOMs to a separate directory.
--containerizedBuild for Kubernetes rather than host installation.
--no-pullReuse or build a local builder image without pulling it.
--helpShow all options.

For example, build DEB and RPM packages with glibc 2.39 and its paired GCC 13:

bash
./dockerfiles/chainguard/build.sh --glibc 2.39 -f deb,rpm

Each baseline and architecture gets a separate default build directory. Kubernetes builds also add -containerized to the directory name. If you use -b, keep separate directories for different toolchains and build modes.

The default glibc 2.34 baseline targets Ubuntu 21.10 or later, Rocky 9 or later, and Wolfi. Rocky 8 is not supported. Newer baselines require newer target libraries.

Run CMake Directly ​

Use cmake-chainguard.sh to run a CMake command inside the builder with the same arguments:

bash
./dockerfiles/chainguard/cmake-chainguard.sh --version

It defaults to glibc 2.34 and GCC 11. Set CHAINGUARD_GLIBC and CHAINGUARD_GCC to override them.

The proxy runs only the requested CMake command. It does not supply HPCC's configure flags, build automatically, or create packages. Use build.sh for the complete HPCC build.

Build a Development Image ​

The build script handles this automatically. To prepare the default image separately:

bash
./dockerfiles/chainguard/create-build-image.sh --glibc 2.34

Run create-build-image.sh with --help for options.

CI Image Freshness ​

LN's default Chainguard CI build rebuilds its selected development image on every run using create-build-image.sh --rebuild. The development-image publishing workflow uses the same option. It bypasses both published/local image reuse and Docker's layer cache, and pulls the current base-image tags. Toolchain builds refresh the Ubuntu sysroot packages and upgrade Wolfi packages without changing the selected glibc baseline or GCC major.

An explicitly supplied builder image is pulled before use; pull failures stop the build rather than silently reusing an old local image. --no-pull explicitly opts out, including when CI needs to use its freshly rebuilt local builder. Packaging layers are rebuilt without cache and upgrade installed Wolfi packages. They deliberately use the selected local base instead of pulling it a second time, which would replace CI's newly rebuilt builder with the published one. For sysroot builders, packaging layers also reapply the toolchain's include-fixed cleanup after APK operations so GCC updates cannot restore Wolfi glibc headers that take precedence over the selected sysroot.

CI pulls runtime bases and disables layer reuse for both the runtime audit and the published runtime image. The isolated runtime rootfs installs current APK packages, and the R-package build stage upgrades its installed packages. The distroless JDK/FIPS runtime has no package manager: its inherited packages are refreshed by pulling the current configured upstream image. Explicit version constraints (including Python/GCC compatibility, Mono, NuGet, and syft) remain in place; unsupported upstream images cannot acquire updates no longer published.

For local development, create-build-image.sh --no-pull still reuses an existing image. Use --rebuild to force a fresh one:

bash
./dockerfiles/chainguard/create-build-image.sh --glibc 2.34 --rebuild

The image-selection regression tests run without a container engine:

bash
python3 -m unittest discover -s dockerfiles/chainguard/tests -v

Runtime Image Audit ​

The runtime-audit target in Dockerfile.runtime checks the assembled runtime before the final image can be built. Its Python check uses the native HPCC compiler, eclcc -Me, to evaluate a foldable EMBED(Python3) function inside the runtime-python-audit stage, derived from runtime with its user, working directory and environment. Docker supplies /proc in this stage; HPCC needs /proc/self/exe to discover its plugin path, so this check must not run in a bare copied-root chroot. The function reads sys.version_info; its result must match RUNTIME_PYTHON, which must also match PYTHON in the packaged hpcc-baseline. Missing libraries, plugin initialization/evaluation failures, and version mismatches fail the audit rather than bypassing it.

The runtime-audit target retains the filesystem, dependency and SBOM checks and requires the Python-stage success marker. The final image in turn requires the runtime-audit success marker, so neither audit can be skipped.

Do not test libpy3embed.so with Python's ctypes.CDLL. This is an HPCC embedding plugin, not a Python extension: its global initialization initializes the interpreter and releases the GIL with PyEval_SaveThread. Loading it from an already-running Python interpreter interferes with that host's interpreter and thread state. The previous ctypes audit segfaulted (exit 139) with Python 3.12; that failure alone does not establish a packaging or ABI defect. Native ECL evaluation exercises the supported embedding path instead. This smoke check does not replace the Python embedding regression suite or prove that every distributed query works.

LN Builds ​

To build LN, run its wrapper from the LN repository root instead:

bash
./dockerfiles/chainguard/build.sh

The wrapper uses the sibling HPCC-Platform checkout for tooling, reads LN's .env, and writes to ../build/chainguard-glibc2.34-gcc11/. Use -s /path/to/HPCC-Platform to select another checkout.
